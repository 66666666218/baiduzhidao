## 1. 背景与目标

旧版《百度知道情感类答题助手》（位于 `D:\code\baiduzhidao`，Electron 打包，可从 app.asar 完整还原源码）
实现了围绕百度知道 21 周年活动页（`zhidao.baidu.com/hd/21th_activity/`）的全自动答题流水线：

```
爬题入库 → 随机抽题 → AI 生成回答 → 复制/自动提交 → 通过数核对
（多账号：比特浏览器轮换，每账号每日限额）
```

**v2 目标：在不改变核心业务流程的前提下，重写为可维护、可扩展、可测试的工程化版本。**

非目标（本期不做）：
- 不更换目标平台（仍围绕百度知道活动页）
- 不做账号注册/养号功能
- 不引入需要构建链的前端框架（保持零构建，见 §3 决策）

## 2. 旧版分析：问题清单

旧版全部源码约 71KB `main.js` + 98KB `zhidao.js` + 61KB `renderer.js`，功能完整但有以下问题：

| # | 问题 | 具体表现 | 影响 |
|---|------|----------|------|
| P1 | **单文件巨石** | main.js 同时管 IPC、设置、题库、Excel、AI、路径迁移 | 无法测试、改一处怕崩全局 |
| P2 | **选择器散落** | `.answer-section__question` 等 30+ 处选择器硬编码在流程代码里 | 百度改版要全文搜索修改 |
| P3 | **题库三写** | 每加一题同时重写 JSON + TXT + XLSX 三个全量文件（5000+ 条） | IO 放大，XLSX 被占用就要写“临时备份” |
| P4 | **流程即架构** | runZhidaoDrafts/runCrawlQuestions/runSubmitAnswerQueue 三个 200 行 while 循环，去重/进度/延迟/停止逻辑互相复制 | 无法复用，行为不一致 |
| P5 | **串行 AI** | AI 生成串行 + 文件锁，一个号生成时其他号干等 | 吞吐低 |
| P6 | **隐藏遥测** | 硬编码上报心跳到 control.bdmianjin.com | 隐私风险，用户不可关 |
| P7 | **无测试** | 0 个自动化测试；调试靠日志 | 回归全靠手点 |
| P8 | **适配器单绑** | 比特浏览器 API 写死在流程里 | 无法换 AdsPower/普通 Chrome |

## 3. 关键技术决策（含理由）

| 决策点 | 选择 | 备选 | 理由 |
|--------|------|------|------|
| 桌面框架 | Electron + 原生 HTML/CSS/JS（零构建） | Vue/React + Vite | 旧版维护者熟悉；UI 简单（表单+表格+日志），框架收益低于工具链成本 |
| 浏览器自动化 | playwright-core + CDP（连接外部浏览器） | puppeteer-core / 直连 CDP | 沿用旧版已验证方案；playwright 的 locator/evaluate 降级策略成熟 |
| 存储 | **单源 JSON 存储 + 按需导出**（内存索引 + 原子写 + 追加日志） | SQLite (better-sqlite3) | 避免 native 模块跨 Electron 版本重编译；5000 条 JSON 全量写 <100ms，配合防抖足够。SQLite 列入待决策（数据量到 5 万条再上） |
| LLM 接入 | OpenAI 兼容 chat/completions，baseURL/model 可配 | 各家 SDK | 硅基流动/DeepSeek/通义/Kimi 全兼容，一套代码 |
| 浏览器适配 | 适配器接口 + BitBrowser 实现 | 只支持比特 | AdsPower 等留接口（见待决策 #1） |
| 打包 | electron-builder 配置就绪，**默认不打包** | 直接出安装包 | 打包需下载 ~100MB 二进制且耗时；是否出正式安装包待用户决策 #2 |
| 遥测 | **完全移除** | 改为默认关闭的可选开关 | 隐私优先；需要统计再告知（待决策 #5） |
| Node 版本 | ≥ 20（开发机为 26） | — | 内置 fetch / node:test |

## 5. 核心设计

### 5.1 选择器集中（P2）

`pages/selectors.js` 导出一个 `SEL` 对象，页面操作代码只允许引用 `SEL.*`：

```js
module.exports = {
  activityUrl: "https://zhidao.baidu.com/hd/21th_activity/",
  zone:  { cards: ".answer-section__question", cardTitle: ".answer-section__question-title",
           goAnswerBtn: ".answer-section__btn", zoneTabText: "答题区", categoryText: "情感类" },
  pager: { activeNum: ".answer-section__pager-num.is-active",
           jumpInput: ".answer-section__pager-jump-input", nextPattern: /next|right|pager-next|下一页/ },
  question: { titleCandidates: ["h1", ".question-title", "[class*='title']"],
              editorCandidates: [".ueditor", ".question-answer textarea", "[contenteditable='true']"],
              submitCandidates: [".answer-button", "button:has-text('提交回答')"] },
  verify: /百度安全验证|请完成下方验证|滑动完成拼图|验证码|verify|captcha/i,
};
```

页面改版 → 只改这一个文件 + 跑 E2E。每步操作保留旧版的“locator 失败 → DOM evaluate 降级 → 诊断 dump”三级策略。

### 5.2 任务引擎（P4）

```js
class TaskManager {
  async start(kind, payload)     // 同一时刻仅一个任务；kind: crawl|generate|submit|passed
  stop()                         // 协作式停止
  updateLiveSettings(patch)      // 运行中热更新（AI key/模型/延迟等）
}
```

所有任务共享同一骨架：`打开环境 → 页面就绪检查(验证码检测) → 循环{取一项 → 处理 → 记进度 → 随机延迟}`。
差异点用参数表达：取项函数、处理函数、配额规则。进度/停止/热配置只在引擎实现一次。

### 5.3 存储（P3）

- `bank.json`：题库单源；内存 Map（url/title/content 三键索引）；写入 = 防抖 500ms 原子写（tmp+rename）
- `answers.json`、`progress.json`、`used-keys.json` 同模式
- TXT/XLSX **仅在用户点击“导入/导出”时生成**，不再每题三写
- 提交/爬取断点续跑：进度文件记录每个环境处理到的 (页码, 已用题键)

### 5.4 AI 客户端（P5）

- OpenAI 兼容 `/chat/completions`；超时 120s；可重试错误（429/5xx/网络）指数退避 ×3
- `concurrency` 可配（默认 2），信号量控制
- 记录每次调用的 token 用量到 `usage.json`，UI 展示累计费用估算
- Prompt 沿用旧版情感类模板，标题/内容模板支持 `{{标题}} {{问题内容}}` 占位符

### 5.5 浏览器池（P8）

```js
class BrowserPool {
  constructor(adapter)            // adapter: BitBrowserAdapter（本期）
  async acquire(envName)          // 打开环境 → 返回 { cdpUrl, close() }
  async release(handle)
}
// adapter 接口：listByName(name) / open(id) / close(id)
```

### 5.6 渲染端 UI

8 个视图沿用旧版信息架构（比特环境/题目爬取/随机抽题/生成答案/复制答案/自动提交/常用网址/运行日志），
视觉简化为一套 CSS 变量；所有账号字段支持打码显示。

### 10.3 开发中修复的关键问题（存档）

1. **Electron 二进制下载**：npm 11 拦截 postinstall + GitHub 网络重置 → npmmirror 镜像 + `scripts/install-electron-bin.js` 手动解压兜底
2. **Edge 启动器秒退**：msedge.exe 父进程立即退出（浏览器在子进程树），stderr 等 "DevTools listening" 不可靠 → 固定调试端口 + 轮询 `/json/version`
3. **contextBridge 命名冲突**：`exposeInMainWorld("api")` 在 window 上是不可配置属性，渲染端顶层 `const api` 抛 SyntaxError → 冒烟自检抓到后改名 `rpc`
4. **normalizeQuestion 白名单**：丢失 `submittedAt` 导致提交时间不落盘 → E2E 断言抓到后补上

## 11. 第二轮自主审查记录（2026-09-10 凌晨 · 循环自问自答）

审查方法：对每个关键节点自问"它满足项目需求吗？失效会怎样？"，发现问题 → 修复 → 补测试 → 下一个。

### 修复的问题（按发现顺序）

| # | 严重度 | 自问的问题 | 发现的缺陷 | 修复 | 验证 |
|---|--------|-----------|-----------|------|------|
| 1 | P0 | 生成完答案直接去提交，会发生什么？ | 生成结果不写回 Excel，提交环节从表格读行时 answer 全空被过滤，**工作流断链**（旧 E2E 用内存行提交所以没暴露） | 生成任务按原始索引回填 + 周期性/结束安全写回表格；支持重复行去重回填 | 新增 E2E 回环测试 |
| 2 | P0 | 用户把同一张表提交两次会怎样？ | 已提交的行会**重复提交**，浪费账号额度 | 提交任务默认跳过 status=已提交 的行（可勾选强制重交） | 新增单元测试 |
| 3 | P0 | 填答失败时用户怎么办？ | 日志声称"答案已复制到剪贴板"但实际**没有复制** | deps 注入 copy 回调，失败时真正写剪贴板 | E2E 链路覆盖 |
| 4 | P1 | 题库已有 9950 条再跑爬题会怎样？ | seenKeys 为空，已入库的题被**全部重新打开**（慢且浪费） | 任务开始预载同分类题库标题进去重集合 | E2E 全链路覆盖 |
| 5 | P1 | 爬到 3000 条时崩了怎么办？ | 只能手动改起始页重爬 | byEnv+分类记录断点页码，UI 加"断点续爬"开关 | 新增单元测试 |
| 6 | P1 | 比特浏览器拦截弹窗时爬题会怎样？ | 题目页=活动页，**活动页标题/URL 被当题目入库**（脏数据） | 校验 URL 非活动页 + 标题匹配才入库，否则跳过并计数 | E2E 覆盖 |
| 7 | P1 | 强杀进程/直接关窗口会丢数据吗？ | 防抖写入窗口内（500ms）的数据丢失 | before-quit → store.flushAll() | 代码审查 |
| 8 | P1 | 答案记录上万条后 upsert 会怎样？ | 每次 unshift 后**全量重建索引 O(n)** | 索引改为 Map<key,item>，就地合并 O(1) | 既有单测通过 |
| 9 | P2 | 新用户装完软件怎么知道能不能跑？ | 必须先配比特浏览器+AI Key 才能验证 | **一键自检**：内置模拟站+无头 Edge，6 步跑通迷你流水线，分步报告耗时与结果 | 新增 E2E + 实测通过 |
